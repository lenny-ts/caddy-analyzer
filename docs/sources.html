Log Sources & Input Protocols

Complete technical specification for reading Caddy v2 access logs

1. Local Log Files & Path Globs

Read directly from local JSON access log files on disk. If positional source arguments are omitted, caddy-analyze automatically checks for local log files in ./access.log, ./caddy.log, ./caddy-access.log, /var/log/caddy/access.log, or /var/log/caddy/caddy.log:

# Single access log file
caddy-analyze /var/log/caddy/access.log

# Multiple files using wildcard globs
caddy-analyze /var/log/caddy/*.log

# Auto-discovery mode (runs against default local log paths)
caddy-analyze

2. Standard Input Pipe -

Use - to pipe structured log content from standard input. This enables seamless integration with unix utilities like cat, zcat, grep, or remote SSH streams:

# Read compressed gzipped log archives
zcat /var/log/caddy/access.log*.gz | caddy-analyze -

# Read remote logs via SSH tunnel
ssh user@remote-server "cat /var/log/caddy/access.log" | caddy-analyze -

3. Docker Containers docker://

Stream JSON logs directly from the Docker daemon socket using container names or container IDs:

# Read logs from a running Docker container
caddy-analyze docker://my-caddy-container

# Real-time log tailing from Docker
caddy-analyze tail docker://my-caddy-container

ℹ Note

Requires permissions to access /var/run/docker.sock. Add your user to the docker group if permission is denied.

4. Kubernetes Pods k8s://

Connects directly to Kubernetes pods using your active kubectl context configuration:

# Read logs from pod in default namespace
caddy-analyze k8s://caddy-pod-abc12

# Specify namespace using -n or --namespace flag
caddy-analyze k8s://caddy-pod-abc12 -n production

5. Systemd Journalctl journalctl://

Reads log streams directly from the systemd journal for Caddy service units:

# Read systemd unit journal
caddy-analyze journalctl://caddy.service

6. Handling Permission Denied Errors

When Caddy log files are owned by root or caddy:caddy with restricted 0600 permissions, caddy-analyzer outputs a helpful diagnostic hint:

⚠ Permission required

error: permission denied reading /var/log/caddy/access.log
💡 Hint: Run with sudo: sudo caddy-analyze /var/log/caddy/access.log
💡 Or add your user to the caddy group: sudo usermod -aG caddy $USER

7. Sample Logs & Test Fixtures

The repository ships two ready-to-use Caddy v2 JSONL fixtures under testdata/, generated by testdata/generate.py. They let you exercise every command — including the full 26-category detection engine — without a live Caddy server or real traffic. All client IPs use TEST-NET ranges (RFC 5737): 192.0.2.0/24 and 203.0.113.0/24 are benign clients, 198.51.100.0/24 are attackers — nothing points at a real host.

Test fixtures shipped under testdata/
FileLinesSizePurpose
testdata/sample.log68~33 KBOne curated entry per detection category plus a benign baseline — verifies all 26 categories fire
testdata/large.log~50,000~27 MBRealistic 24h mixed traffic (~95% benign, ~5% malicious cycling all 26 categories) — throughput demos

Using the fixtures

# Curated sample: confirm all 26 detection categories fire
caddy-analyze --detect testdata/sample.log

# Inline-detect colorized stream on the curated sample
caddy-analyze tail -d testdata/sample.log

# JSON detections keyed by IP
caddy-analyze --detect -f json testdata/sample.log

# Performance / scale demo (~5,200 req/s with detection enabled)
caddy-analyze --detect testdata/large.log

# Standalone HTML report from the curated fixture
caddy-analyze -f html -o report.html --detect testdata/sample.log

# Diff the two fixtures to see attackers stand out from benign load
caddy-analyze diff testdata/sample.log testdata/large.log

Regenerating the fixtures

Both files are produced by a single Python script with no third-party dependencies (stdlib only). The generator writes its output next to itself — always into testdata/, regardless of the current working directory:

python3 testdata/generate.py            # regenerate both sample.log and large.log
python3 testdata/generate.py --sample  # only sample.log
python3 testdata/generate.py --large   # only large.log

sample.log is deterministic (one entry per detection category in fixed order), and large.log uses a seeded RNG for the benign background, so re-running the script produces byte-identical output. Timestamps are anchored at epoch 1785148418.0 (2026-08-20) and match the fixtures used by parser_test.go.

ℹ Note

The generator script is the source of truth for these fixtures. Please don't hand-edit the .log files. If you need a different traffic mix (more attack traffic, a different time window, larger volume), edit testdata/generate.py and re-run it.
